# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

qrec is a Windows-only screen area recorder, written in Rust with egui/eframe 0.36 and the `windows` crate. It records a rectangle of one monitor to an MP4 (H.264, AAC) with the sound the computer plays and the pointer, from a window of a few options and a global hotkey, and trims a recording without re-encoding in a second window. Priorities: a minimal interface, no external runtime (no FFmpeg, no .NET), hardware encoding when the GPU has it. `README.md` / `README.ru.md` are the user-facing docs and must be kept in sync (both languages, cross-linked, formal tone, no imperatives).

## Commands

```
cargo build --release                  # target\release\qrec.exe
cargo test                             # unit tests (geometry, settings round trips, audio conversion, cursor masks, H.264 parameter sets, icon)
cargo clippy --all-targets             # must stay warning-free
python tools/make_release.py           # tests, release build, dist\qrec_<ver>_Setup.exe (Inno Setup 6, tools/setup.iss) and _portable.zip
python tools/make_release.py --no-tests --install   # the same, then installs it silently over the installed copy
$env:QREC_TRACE=1; .\target\debug\qrec.exe          # what the recording does, on stderr (debug build has a console)
.\target\debug\qrec.exe --record 5 --region 100,100,1280,720 [--monitor 2] [--fps 60] [--quality high] [--no-audio | --audio-app name.exe [--no-boost]] [--no-cursor] [--border] [--out file.mp4]
                                       # a recording without the window, from a console; checks the pipeline end to end
.\target\debug\qrec.exe --cut in.mp4 --from 2.3 --to 4.5 [--out file.mp4]   # a cut without the window (from the key frame at or before --from)
.\target\debug\qrec.exe --info in.mp4   # size, fps, length, the times of the key frames (and how long listing the frames took)
.\target\debug\qrec.exe file.mp4        # the window with the trimming window open on the file
.\target\debug\qrec.exe --test-select  # opens the selection overlay and drives it with posted mouse messages (the screen dims for a moment)
.\target\debug\qrec.exe --export-icon file.ico|file.png   # the app icon for the installer / the README
cargo run --example wasapi_probe       # whether WASAPI capture streams can be opened on this machine (see Architecture: audio)
cargo run --example process_loopback   # whether the process loopback works and delivers timestamps
cargo run --example app_loopback       # how the loopback of one program follows its mixer volume and the master volume (plays a tone)
.\target\debug\examples\app_loopback.exe play 0.25 9   # a tone at 25 % in the mixer, to record with --audio-app app_loopback.exe (comes out at -23 dBFS RMS)
```

## Architecture

The recording is a pipeline of threads started by `recorder::Recorder::start`:

- **`capture.rs`**: Desktop Duplication of one monitor on the adapter that drives it. Only the recorded area is copied out of each frame, into a BGRA texture of the area's size (`Capturer::frame`). Frames come only when the desktop changes; a frame that only reports a pointer move is not copied. The pointer position and shape are kept in `Capturer::cursor`. `DXGI_ERROR_ACCESS_LOST` (a mode change, the secure desktop) is reported as `PollError::AccessLost` and the recorder recreates the duplication, encoding the last frame meanwhile. HDR displays (16-bit float frames) are refused with a message. Rotated displays come in their native orientation.
- **`cursor.rs`**: the pointer drawn into a copy of the frame by a pixel shader (compiled at run time with `D3DCompile`), over a patch of the frame copied from under it, so monochrome (AND/XOR) and masked-colour shapes invert or XOR correctly. The captured frame stays clean so a still desktop does not leave pointer trails.
- **`convert.rs`**: BGRA to NV12 with the Direct3D 11 video processor (auto-processing off, RGB full range to BT.709 studio), into a pool of NV12 textures. A pooled texture is reused only when its COM reference count is back to the idle value, so a texture still held by the encoder is never overwritten; the pool grows when all are busy (it stays at 4 with the direct encoder).
- **`venc.rs`**: the H.264 encoder as a Media Foundation transform driven directly (hardware ones are asynchronous: `METransformNeedInput` / `METransformHaveOutput` events are pumped on each frame; the software one is synchronous and gets frames read back to system memory). Why not let the sink writer encode: it then queues about two seconds of *input* frames per stream for interleaving, each a texture in video memory (68 textures at 30 fps, 138 at 60; measured, independent of `MF_LOW_LATENCY` and of the encoder). With compressed samples the sink writer queues bytes instead.
- **`encoder.rs`**: the MP4 file through the sink writer with throttling disabled: the H.264 stream passed through (its media type gets `MF_MT_MPEG_SEQUENCE_HEADER` from the SPS/PPS of the first sample when the encoder did not set it), the AAC stream encoded by the sink writer from 16-bit stereo PCM. The file is opened with the first encoded frame; audio that comes earlier waits in `pending_audio`.
- **`audio.rs`**: WASAPI loopback, of the whole system (`audio::Source::System`) or of one program (`Source::App`, its exe name). *Process loopback* first (`ActivateAudioInterfaceAsync` with `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`, excluding this process's tree; Windows 10 2004+): the format is the program's choice (48 kHz 32-bit float stereo, turned into 16-bit for the encoder), the stream runs on while nothing plays, packets carry QPC timestamps. One program is the process loopback *including* its tree (no fallback); with `boost` (the window's **Boost** checkbox) multiplied by `sessions::Volume::gain`, ramped across a packet when it changes. The endpoint loopback (`AUDCLNT_STREAMFLAGS_LOOPBACK` on the default output, with a silent render stream to keep packets flowing) is the fallback. On the development machine every endpoint *capture* stream, loopback or microphone, fails with `E_INVALIDARG` from `Initialize` (confirmed with the `wasapi` crate and PyAudioWPatch too), while the process loopback works: the fallback is untested here. The `PROPVARIANT` of the activation parameters is wrapped in `ManuallyDrop`: the crate's `PROPVARIANT` clears itself on drop, which would free the blob pointer into the stack (heap corruption, exit code 0xC0000374).
- **`sessions.rs`**: the programs with audio sessions on the active output devices (the Volume Mixer's; by exe path, named by `FileDescription` with the first differing folder when two have one name, whether playing), the process to capture for an exe path or name (the topmost of its processes, a browser plays from a child; of several copies the one playing now, then one with a session), and the gain that undoes the mixer volume `v` of its sessions: `1/v` (the loudest unmuted session, floor 1 %; sessions listed again every second). Measured with `examples/app_loopback.rs`: the loopback of another process hears it after its session volume, linearly (25 % is −12 dB); a process that captures itself has it applied twice (its capture stream is in the same session), which once looked like `v²`. The master volume does not reach it here (the device has hardware volume, `QueryHardwareSupport`); with software volume this is untested.
- **`recorder.rs`**: the clock is `QueryPerformanceCounter` in 100 ns units (`win::qpc_100ns`), shared by video ticks and WASAPI packet timestamps. The video thread encodes at a fixed rate (a tick every 1/fps with the last frame; ticks skipped when behind, counted as `dropped`). The audio thread writes packets at their own timestamps and fills gaps over 30 ms with silence, trims overlaps. Bitrate = pixels × fps × bits-per-pixel of the quality (0.05 / 0.1 / 0.2), clamped to 0.5..60 Mbit/s.
- **`overlay.rs`**: two Win32 windows on their own threads. The selection covers the virtual screen with a per-pixel-alpha layered window (`UpdateLayeredWindowIndirect` with a dirty rectangle; a DIB of the whole virtual screen), takes mouse coordinates from the messages (so `--test-select` can post them), and fits the drag to the monitor it started on (`Region::fit`: even sides, at least 64 px). With fixed proportions (`Aspect`) `Region::drag` keeps the start corner and makes the width follow the pointer in steps of 2 px with the height of the ratio rounded to an even number (`height_for`: within a pixel of 16:9, exact at 1280×720 and 1920×1080), as large as fits on the monitor; `Region::with_aspect` brings an area already chosen to new proportions around its centre. The main window is hidden (`ShowWindow`, not a viewport command: eframe may not run `update` for a hidden window, so the app could not notice the end of the selection) while it is open, and the selection's thread shows it again when it closes. The frame around the recorded area is a colour-keyed layered window, click-through, 3 px outside the area. Both are excluded from capture.
- **`hotkey.rs`**: `RegisterHotKey` on a thread with a message loop; the chord is chosen in the window by pressing keys (`Chord::from_egui`), letters, digits and F1–F12 only, and must have a modifier unless it is a function key.
- **`tray.rs`**: the notification area icon on its own thread, with a hidden top-level window (a message-only one would miss the `TaskbarCreated` broadcast after an Explorer restart). `NOTIFYICON_VERSION_4`; the icon is the app's, red with a white dot while recording (`icon::recording_rgba`), the clock in the tooltip. A click sends `Command::Show`, the menu `Toggle` / `Show` / `Taskbar` / `CloseToTray` / `MinimiseOnRecord` / `TrimAfterRecord` / `About` / `Exit`; the app handles them in `poll` like the hotkey. For a minimised or hidden window eframe 0.36 runs no egui pass and calls `App::logic` instead of `ui` (throttled); `logic` runs `poll` too, or a recording could not be stopped by the hotkey or the tray while the window is minimised (`minimise_on_record`). Without a taskbar button (`taskbar` setting, only while the icon exists) the window is a tool window (`win::set_taskbar_button`): winit forces `WS_EX_APPWINDOW` and rewrites the extended style whenever it changes the window's state, so the app sets it again each frame; the minimise button then hides the window. With `close_to_tray` only the window's own cross hides it: `WM_CLOSE` from outside (the installer's Restart Manager, `make_release.py`'s `taskkill`, Alt+F4) still closes the program and saves the settings.
- **`trim.rs`**: the cut without re-encoding. A source reader opens the file with its compressed streams (found by subtype: H.264 and AAC; the others deselected), seeks to the start (the MP4 source lands on the sync sample at or before it) and the samples are passed to a sink writer with their times moved back; the copy starts on the first key frame delivered (`MFSampleExtension_CleanPoint`), audio heard before it waits in `pending_audio`, and each stream is deselected once its samples reach the end. `frames` lists every video sample (time, duration, key frame; 0.01 s for 180 frames). `Preview` decodes one frame at a time: the video stream set to RGB32 with `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING` (software decoder, no DXGI manager), reading on when the frame wanted is ahead within the GOP and seeking otherwise, the pixels averaged down by a whole factor to at most 1920 px a side (`IMF2DBuffer` for the pitch, bottom-up when negative). `venc.rs` asks for a key frame every second (`MF_MT_MAX_KEYFRAME_SPACING = fps`; the NVIDIA encoder honours it), so a cut can start within a second of any frame.
- **`editor.rs`**: the trimming window, an immediate viewport of the main window (`show_viewport_immediate`, drawn when the main window's `ui` runs; its panels are painted over `panel_fill`, as `clear_color` is transparent for every viewport). Opened by **Trim…** beside the last file, by an `.mp4` dropped on the window, by a file on the command line, or when a recording ends with the tray's **Trim after recording**. Two threads per file: the preview (sends the headers first, then decodes the latest frame asked for) and the frame list; a cut runs on a third with `trim::Progress`. Keys are taken from `events` in order (several arrive in one frame when posted). The start mark snaps to the key frame at or before; the end is the first frame left out. The window is not excluded from capture.
- **`app.rs`**: the egui window; `display.rs` lists the monitors from DXGI (`\\.\DISPLAYn` identifies one between runs); `region.rs` is the geometry; `win.rs` the Win32 helpers; `i18n.rs` the `tr!` macro; `icon.rs` the procedural icon (also compiled by `build.rs` for the `.ico` and the window icon); `cli.rs` the command line modes.

Every window of the program (the main one, the selection, the frame) is excluded from captures with `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`, which Desktop Duplication honours; `QREC_NO_EXCLUDE=1` leaves them visible, to look at them in a recording. A window hidden (`SW_HIDE`) and shown again keeps the affinity but comes out as a black shape in the capture (minimise and restore do not do this; the old builds had it after every area selection): `win::show_window` and `win::set_taskbar_button` set it anew (`WDA_NONE`, then `WDA_EXCLUDEFROMCAPTURE`) after showing.

## Conventions

- Every user-visible string goes through `tr!("English", "Русский")`; the language follows the Windows UI language unless one is chosen in About (`i18n::LangChoice`, applied at once: `tr!` is evaluated every frame). Log messages stay English.
- Persisted state (eframe storage, `%APPDATA%\qrec\data\app.ron`, or `app.ron` beside the exe when that file exists: portable mode): `monitor` (device name), `region` (`x,y,w,h` on the virtual screen, empty for the whole display), `fps` (`30`/`60`), `quality` (`low`/`medium`/`high`), `audio`, `audio_app` (full path of the exe, or its file name as `--audio-app` takes it; empty for the whole system), `audio_boost` (`true`), `cursor`, `folder`, `hotkey` (`Ctrl+Alt+R`, empty when removed), `aspect` (`free`/`16:9`/`1:1`), `taskbar` (`true`; `false` keeps the window off the taskbar), `close_to_tray` (`false`), `language` (`system`/`en`/`ru`), `minimise_on_record` (`false`; `App::minimise` hides instead of minimising when the window is off the taskbar), `trim_after_record` (`false`; the recording opens in the trimming window when it ends, the main window shown again first, since the trimming window is drawn with its pass).
- The release profile has `panic = "abort"` and no console; a panic shows a message box (`install_panic_hook`). The C runtime is linked statically (`.cargo/config.toml`).
- The version comes from `Cargo.toml` (`main::VERSION`, shown in the window). Between releases it is the next version with `-dev`, and `build.rs` appends `git describe --tags --always`. Release: drop `-dev`, commit, tag `vX.Y.Z` (release.yml checks the tag against `Cargo.toml`), then set the next `-dev` version.
- COM: worker threads initialise the MTA (`win::com_init_mta`); Media Foundation, WASAPI and DXGI objects are used across the recording threads under the encoder's locks. The `windows` crate (not `windows-sys`) is used for its interface wrappers; `windows-core` is a direct dependency only because `#[implement]` expands to paths in it.
- The trimming window is driven for checks with posted messages: `WM_KEYDOWN`/`WM_KEYUP` with the scan code in `lParam` (winit maps keys by it; bit 24 for arrows, Home, End) and `WM_MOUSEMOVE` then `WM_LBUTTONDOWN`/`UP` at client coordinates reach egui; the main window's record button needed a real click (`SetCursorPos` + `mouse_event`), and with `minimise_on_record` the window is minimised when the recording starts (`ShowWindow(SW_RESTORE)` before clicking stop). The window is found by its title (`FindWindowW` fails on the Cyrillic title from PowerShell; `EnumWindows` by process id works).
- GUI checks without a user: the window's OpenGL client area cannot be captured with `PrintWindow`/`BitBlt` on an NVIDIA machine, but a recording *can* show it with `QREC_NO_EXCLUDE=1`: start the window in the background, run `--record` on its area (the window logs `window at (l, t, r, b)` with `QREC_TRACE=1`), extract a frame with ffmpeg and look at the PNG. The same shows the selection overlay (`--test-select` while a recording runs) and the recording frame (`--record --border` while a second recording covers a larger area). Close test windows with `taskkill /PID` (WM_CLOSE, which saves the settings), never leave one open: a launched qrec window takes the focus and the hotkey. Coordinates from a non-DPI-aware tool (PowerShell's `Cursor.Position`) are logical, not physical: multiply by the display scale.
- Measurements on the development machine (i7-13700KF, RTX 4070 Ti SUPER, 3840×2160 at 150 % scaling, Windows 10 22H2): NVIDIA H.264 Encoder MFT is found and asynchronous; 1280×720 at 60 fps with audio runs with 0 skipped frames in a debug build; the first frame is written within about 100 ms of start.
